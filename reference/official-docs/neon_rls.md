## 1. NeonにおけるRow Level Security

Row-Level Security（RLS）は、現在のユーザーに基づいてテーブルの個々の行へのアクセスを制御するPostgresの機能である。Neonは標準Postgresを実行しているため、RLSの構文と意味論は素のPostgresと同じである。

Neonはその上に2つの要素を加えている。

1. **Data API** — データベースに対するPostgREST互換のRESTエンドポイント。ブランチごとに有効化する。ブラウザから到達可能であるため、これを安全にするのがRLSの役割である。
2. **JWT → SQL の受け渡し** — Data APIがJWTを検証（JWKS）し、`pg_session_jwt` 拡張が提供するヘルパー関数を通じてユーザーIDをポリシーへ渡す。

```sql
-- テーブルでRLSを有効にする
ALTER TABLE notes ENABLE ROW LEVEL SECURITY;

-- 自分のnotesにのみアクセスできるポリシーを作成する
CREATE POLICY "users_can_only_access_own_notes"
ON notes FOR ALL
TO authenticated
USING (auth.user_id() = user_id);
```

**RLSは自動的には有効にならない。** SupabaseのTable Editorとは異なり、Neon ConsoleやSQLでテーブルを作成してもRLSは **オフのまま** である。RLSなしでData APIに公開されたテーブルは、すべての認証済みユーザーが全行を読める。

---

## 2. アクセス制御の2層

Data APIは独自の権限体系を持たない。すべてをPostgresへ委譲しており、その層は2つある。

1. **ロール権限（`GRANT`）** — APIがそのテーブルに触れてよいか
2. **Row-Level Security（RLS）** — そのユーザーがどの行を見てよいか

両方が正しくなければならない。RLSなしで `SELECT` を付与すれば全行が露出し、`GRANT` なしでRLSを有効にすれば権限エラーになる。

### APIのロール

Data APIはリクエストを受けると、`Authorization` ヘッダーに応じてPostgresロールを切り替えてからクエリを実行する。

| ロール | 使われる場面 | 既定の権限 |
| ------ | ------------ | ---------- |
| `authenticated` | 有効なJWTを伴うリクエスト。`sub` クレームが「誰か」を示し、ロールが「アプリが触れてよい範囲」を定義する | Data API有効化時に「Grant public schema access」を選ぶと `public` に付与される |
| `anonymous` | ユーザーのサインインを伴わないリクエスト（匿名トークンとしてJWTは使用する） | **なし。** 公開データを見せる場合は `SELECT` を明示的に付与する |
| カスタム | JWTの `role` クレーム（例：`"role": "admin"`）を読み、その名前のPostgresロールへ切り替える | 自分でロールを作成し権限を付与する必要がある |

Neon Authでの匿名アクセス：

```js
import { createClient } from '@neondatabase/neon-js';

const client = createClient({
  auth: { url: import.meta.env.VITE_NEON_AUTH_URL, allowAnonymous: true },
  dataApi: { url: import.meta.env.VITE_NEON_DATA_API_URL },
});

// サインイン不要。SDKが匿名JWTを取得してキャッシュする
const { data, error } = await client.from('public_items').select('*');
```

### 第1層：テーブル権限

ConsoleからData APIを有効化する際に **Grant public schema access** をチェックすれば自動適用される。そうでない場合は次を実行する。

```sql
-- 1. スキーマへのUSAGE権限
GRANT USAGE ON SCHEMA public TO authenticated;

-- 2. 既存テーブルへの権限
GRANT SELECT, UPDATE, INSERT, DELETE ON ALL TABLES
  IN SCHEMA public TO authenticated;

-- 3. 今後作成されるテーブルへ自動的に権限を付与
ALTER DEFAULT PRIVILEGES IN SCHEMA public
  GRANT SELECT, UPDATE, INSERT, DELETE ON TABLES TO authenticated;

-- 4. シーケンスへの権限（自動採番IDに必要）
GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA public TO authenticated;
```

テーブル作成直後の「permission denied」エラーは、通常この権限不足が原因である。

## 3. Row Level Securityの有効化

```sql
ALTER TABLE "table_name" ENABLE ROW LEVEL SECURITY;
```

RLSを有効にすると、**ポリシーを作成するまでData API経由ではデータに一切アクセスできなくなる。**

### RLSの3つの状態

| 状態 | 挙動 |
| ---- | ---- |
| **RLS無効** | すべての認証済みユーザーが全行を見られる（絞り込みが一切ない） |
| **RLS有効・ポリシーなし** | すべてのアクセスがブロックされる（何も見えない） |
| **RLS有効・ポリシーあり** | ポリシーのルールで行が絞り込まれる（通常は `auth.user_id()` を使用） |

「クエリが空配列を返す」という症状のほとんどは、中央の状態（RLSを有効にしたがポリシーを作っていない）が原因である。

### ConsoleでRLSの状態を確認する

**Data API** ページにテーブルごとのRLS状態が表示される。RLSが無効なテーブルには次のような警告が出る。

> 「table_name has RLS disabled. All authenticated users can view all rows in this table(s).」

**Enable RLS** ボタンでSQLを書かずに有効化できる。**Tables** ページにはポリシーのテンプレート（例：「based on user_id」）もあり、Data API使用時は `auth.user_id()` に対応づけられる。

## 4. ポリシー

ポリシーはPostgresのルールエンジンである。各ポリシーはテーブルに紐づき、そのテーブルにアクセスするたびに評価される。すべてのクエリに暗黙の `WHERE` 句が追加されると考えればよい。

```sql
create policy "Individuals can view their own todos."
on todos for select
to authenticated
using ( (select auth.user_id()) = user_id );
```

上記は、ユーザーがtodosテーブルをselectしようとしたとき、実質的に次のように変換される。

```sql
select *
from todos
where auth.user_id() = todos.user_id;
-- ポリシーが暗黙的に追加される
```

### ヘルパー関数

Data APIは、現在のリクエストのJWTを読む次のSQL関数を提供する（`pg_session_jwt` 拡張由来）。

| 関数 | 戻り値 | 使う場面 |
| ---- | ------ | -------- |
| `auth.user_id()` | `sub` クレームを `text` で | ユーザーID列が `text` の場合 |
| `auth.uid()` | `sub` クレームを `uuid` で（`sub` が有効なUUIDでなければ `NULL`） | ユーザーID列が `uuid` の場合 |
| `auth.session()` | JWTのペイロード（JSON） | 他のクレームが必要な場合（例：`auth.session()->>'tenant_id'`） |

> ⚠️ **Supabaseとは命名が異なる。** Supabaseでは `auth.uid()` が正式な関数で `uuid` を返す。Neonでも `auth.uid()` は `uuid` を返すが、Neonのドキュメントやテンプレートで **既定的に使われるのは `auth.user_id()`（`text` を返す）** である。列の型に合うほうを選ぶこと。型が合わないとポリシーがエラーになるか、何も返さないまま静かに失敗する。

### `user_id` 列のパターン

```sql
CREATE TABLE posts (
  id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  user_id text DEFAULT (auth.user_id()) NOT NULL,  -- 現在のユーザーが自動設定される
  content text NOT NULL
);
```

ヘルパー関数を列の `DEFAULT` に使うことで、クライアントがINSERT時にユーザーIDを送る（あるいは偽装する）余地がなくなる。

## 5. ポリシーの作成

### SELECTポリシー

```sql
-- 1. テーブル作成
create table profiles (
  id uuid primary key default gen_random_uuid(),
  user_id text not null default (auth.user_id()),
  avatar_url text
);

-- 2. RLSを有効化
alter table profiles enable row level security;

-- 3. ポリシー作成（全体公開の読み取り）
create policy "Public profiles are visible to everyone."
on profiles for select
to anonymous, authenticated
using ( true );
```

自分のプロフィールのみ閲覧できるようにする：

```sql
create policy "User can see their own profile only."
on profiles for select
to authenticated
using ( (select auth.user_id()) = user_id );
```

### INSERTポリシー

```sql
create policy "Users can create a profile."
on profiles for insert
to authenticated
with check ( (select auth.user_id()) = user_id );
```

### UPDATEポリシー

```sql
create policy "Users can update their own profile."
on profiles for update
to authenticated
using ( (select auth.user_id()) = user_id )
with check ( (select auth.user_id()) = user_id );
```

### DELETEポリシー

```sql
create policy "Users can delete a profile."
on profiles for delete
to authenticated
using ( (select auth.user_id()) = user_id );
```

### FOR ALL（読み書きを1つのポリシーで扱う）

```sql
create policy manage_own_posts on posts
for all
to authenticated
using ( auth.user_id() = user_id )
with check ( auth.user_id() = user_id );
```

`USING` は既存のどの行が見える／影響を受けるかを絞り込み、`WITH CHECK` は書き込まれる行を検証する。`WITH CHECK` のない `FOR ALL` は書き込みの条件が不十分になるため、書き込み経路では必ず両方を指定する。

### 公開読み取りと本人限定の書き込みを組み合わせる

```sql
-- 公開済みの行を読める
create policy read_published_posts on posts
for select to authenticated
using (is_published = true);

-- 自分の行にはフルアクセス
create policy manage_own_posts on posts
for all to authenticated
using (auth.user_id() = user_id)
with check (auth.user_id() = user_id);
```

複数の許可（permissive）ポリシーはOR結合される。

### ロールベースのアクセス（例：全行を読めるコーチ／管理者）

ポリシーは通常のSQLであるため、管理者ロールは追加の許可ポリシーとして表現できる。よく使う方法は2つある。

1. **カスタム `role` クレーム** — 既存のPostgresロール名を `role` クレームに入れたJWTを発行し、`TO admin` のポリシーを書く。トークン発行を自分で制御できる場合に有効。
2. **参照テーブル** — `app_admins`（または `team_staff`）テーブルを持ち、ポリシー内で参照する。

```sql
create policy "Staff can read all logs"
on condition_logs for select
to authenticated
using ( exists (
  select 1 from app_admins a where a.user_id = auth.user_id()
) );
```

⚠️ 方法2を採る場合、`app_admins` 自体にもRLSを有効にし、一般ユーザーが書き込めないようにしなければ、このチェックは意味を持たない。

### ビュー（View）

ビューは既定でRLSを **バイパスする**（作成者の権限で実行されるため）。Postgres 15以降では `security_invoker = true` を指定し、クエリ実行者のポリシーが適用されるようにする。

```sql
create view active_athletes
with (security_invoker = true)
as select * from athletes where is_active;
```

### Drizzle ORM

Neonは一般的なパターンに対してDrizzleの `crudPolicy` ヘルパーを推奨している。

```ts
import { sql } from 'drizzle-orm';
import { crudPolicy, authenticatedRole, authUid } from 'drizzle-orm/neon';

export const posts = pgTable('posts', {
  id: bigint({ mode: 'number' }).primaryKey(),
  userId: text('user_id').notNull().default(sql`(auth.user_id())`),
  content: text().notNull(),
  isPublished: boolean('is_published').notNull().default(false),
}, (table) => [
  crudPolicy({
    role: authenticatedRole,
    read: sql`is_published OR (auth.user_id() = ${table.userId})`,
    modify: authUid(table.userId),
  }),
]);
```

`authUid()` は `auth.user_id()` に対応するDrizzleのヘルパーである。読み取りと書き込みで条件が異なる場合は `crudPolicy` ではなく `pgPolicy` を使う。

## 6. Row Level Securityのバイパス ⚠️ 最重要

Neonには「Service role key」に相当するものが存在しない。特権アクセスはPostgres接続を通じて発生し、ここがRLSが気づかないうちに無効化される最大の箇所である。

1. **テーブルのオーナーはRLSをバイパスする。** Postgresでは、テーブルに `FORCE ROW LEVEL SECURITY` を設定していない限り、RLSポリシーはそのテーブルの **オーナー**（およびスーパーユーザー相当のロール）には適用されない。Neonの既定ロール（例：`neondb_owner`）は自分が作成したテーブルのオーナーである。したがって **既定のNeon接続文字列でサーバーサイドから接続するコードは、ポリシーに関係なく全行を読み書きできる。**
2. **`BYPASSRLS` ロール属性** を付与されたロールも同様にバイパスする。
3. **`security_invoker=true` のないビュー** は元テーブルの行を露出させる。
4. **サーバーコード内の直接接続文字列**（Next.jsのServer Actions、APIルート、バッチ処理など）は、1の典型例である。そこではアプリケーション層の認可チェックだけが唯一の防御であり、RLSは何も助けてくれない。

オーナーにもポリシーを強制するには次を実行する。

```sql
ALTER TABLE condition_logs FORCE ROW LEVEL SECURITY;
```

**設計原則:** 「アプリのコードが間違っていても、データベースが他人の行を返すことを拒否する」状態を目標とするなら、ユーザーデータの読み書きは **ユーザーのJWTを使ったData API 経由**（ロール `authenticated`）でなければならない。オーナーロールでのサーバー接続を使う場合は、`FORCE ROW LEVEL SECURITY` を付けるか、適切な `GRANT` を与えた非オーナーのアプリケーション用ロールを用意する。

**Postgresの接続文字列や特権トークンを、決してブラウザへ露出させてはならない。**

## 7. RLSが実際に効いているかの検証

設定の目視確認では不十分である。挙動を検証する。

1. Neon Authでテストユーザー2名（AとB）を作成する
2. Aとしてサインインし、行を1つINSERTする
3. Bとしてサインインし、AのIDを指定してData API経由でその行を要求する
4. レスポンスが空／拒否であることを確認する（行が返ってきてはならない）

手動テスト用のトークン取得：

```bash
# サインインしてセッションクッキーを保存する
curl -X POST 'https://<auth-url>/auth/sign-in/email' \
  -c cookies.txt -H 'Content-Type: application/json' \
  -H 'Origin: http://localhost:3000' \
  -d '{"email":"a@example.com","password":"..."}'

# set-auth-jwt レスポンスヘッダーからJWTを読む
curl 'https://<auth-url>/auth/get-session' \
  -b cookies.txt -H 'Origin: http://localhost:3000' -D - -o /dev/null

# そのユーザーとしてData APIへクエリする
curl 'https://<data-api-url>/rest/v1/condition_logs?select=*' \
  -H 'Authorization: Bearer <JWT>'
```

JWTは約15分で失効する（`"JWT token has expired"` が出たら再サインインする）。

`Authorization` ヘッダーを **付けない** 場合の検証も行う。リクエストは `anonymous` ロールとして実行され、権限がない状態であるべきである。

### よくある失敗パターン

| 症状 | 考えられる原因 |
| ---- | -------------- |
| 誰が実行しても `[]` が返る | RLSを有効にしたがポリシーがない |
| 全員が全データを見られる | RLSが無効、またはリクエストがテーブルオーナーとして実行されている |
| `permission denied for table` | `authenticated` への `GRANT` が不足している |
| 新しいテーブル／列がREST経由で見えない | Data APIの **スキーマキャッシュ** を更新していない |
| トークンが拒否される | 設定したJWT Audienceと `aud` クレームが不一致 |
| RLSが一切適用されない | JWTに `sub` クレームがない |
| ビューから行が漏れる | `security_invoker` を設定していない |

## 8. RLSのパフォーマンス推奨事項

### インデックスを追加する

ポリシー内で使用する列にはインデックスを追加する。

```sql
create index condition_logs_user_id_idx
on condition_logs
using btree (user_id);
```

### 関数は `select` で囲む

ヘルパー関数を `select` で囲むと、Postgresが文単位で結果をキャッシュできる。

```sql
-- パフォーマンスが良い書き方：
create policy "rls_test_select" on test_table
to authenticated
using ( (select auth.user_id()) = user_id );
```

### すべてのクエリにフィルタを付ける

RLSが行を絞り込んでいても、明示的なフィルタを送ることで実行計画が改善する。

```js
const { data } = await client
  .from('condition_logs')
  .select()
  .eq('user_id', userId);  // セキュリティ上は冗長だが、性能面で有効
```

### ポリシーにロールを明示する

`TO` 句を必ず使い、関係のないロールではポリシーが評価されないようにする。

```sql
create policy "rls_test_select" on rls_test
to authenticated
using ( (select auth.user_id()) = user_id );
```

## 9. 運用チェックリスト

- [ ] Data APIを意図した **ブランチ** でのみ有効化している（ブランチごとに設定は独立している）
- [ ] `GRANT` を適用済みである（今後のテーブル向けの `ALTER DEFAULT PRIVILEGES` を含む）
- [ ] ユーザーデータを保持するすべてのテーブルで `ENABLE ROW LEVEL SECURITY` 済みである
- [ ] それらのテーブルにSELECT / INSERT / UPDATE / DELETEの明示的なポリシーがある（または `USING` と `WITH CHECK` の両方を持つ `FOR ALL` ポリシー）
- [ ] `user_id` 列に `DEFAULT (auth.user_id())`（または `auth.uid()`）と `NOT NULL` が設定されている
- [ ] ヘルパー関数と列の型が一致している（`text` か `uuid` か）
- [ ] ポリシーで使う列にインデックスがある
- [ ] APIへ公開するビューに `security_invoker = true` を設定している
- [ ] オーナーロールの接続文字列や特権キーがブラウザへ到達していない
- [ ] サーバーサイドでオーナー接続を使う場合：`FORCE ROW LEVEL SECURITY` または専用の非オーナーロールを用意している
- [ ] ユーザー間アクセスを実測で検証済み（AがBの行を読めない）
- [ ] 未認証アクセスを検証済み（`anonymous` に権限がない）
- [ ] スキーマ変更のたびにスキーマキャッシュを更新している
- [ ] `anonymous` ロールの権限を確認済み（公開したいデータにのみ `SELECT` を付与）

## 付録：Supabase → Neon 対応表（RLS）

| Supabase | Neon |
| -------- | ---- |
| Table EditorでRLSが自動有効 | **自動では有効にならない** — 明示的に有効化する |
| `auth.uid()`（uuid） | `auth.user_id()`（text）／`auth.uid()`（uuid） |
| `auth.jwt()` | `auth.session()` |
| `anon` ロール | `anonymous` ロール |
| `authenticated` ロール | `authenticated` ロール（同名） |
| Service role keyがRLSをバイパス | テーブルオーナーのPostgres接続がRLSをバイパス。HTTP上の同等のキーは存在しない |
| PostgRESTエンドポイント（常時有効） | **Data API**（任意・ブランチごと・DDL後はスキーマキャッシュ更新が必要） |
| 認可情報の格納先としての `raw_app_meta_data` | JWTのカスタム `role` クレーム、またはアプリ側の参照テーブル |
| プロジェクト＝1環境 | ブランチごとの設定（認証・Data API・RLSがまとめて分岐する） |
