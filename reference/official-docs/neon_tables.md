# テーブルとデータ（Neon）

> **出典:**
> - https://neon.com/docs/guides/tables
> - https://neon.com/docs/get-started/query-with-neon-sql-editor
> - https://neon.com/docs/data-api/access-control
> - https://neon.com/docs/data-api/get-started
>
> **取得日:** 2026年7月26日
>
> **前提:** Neonは標準のPostgresを提供する。`CREATE TABLE` などのDDLはPostgresそのままで、Neon独自の方言はない。Neon固有の論点は次の3点である。
> 1. どのUIで作るか（SQL Editor / Tablesページ / クライアント）
> 2. スキーマがブランチごとに分かれること
> 3. Data APIを使う場合に必要な追加設定（GRANT / RLS / スキーマキャッシュ）

Postgresのテーブルを作成し、使用する方法。

テーブルはデータを保存する場所である。テーブルはExcelのスプレッドシートに似ており、列（カラム）と行（ロー）を持つ。

たとえば以下のテーブルは3つの「列」（`id`、`name`、`description`）と4つの「行」を持つ。

| `id` | `name`               | `description`                          |
| ---- | -------------------- | -------------------------------------- |
| 1    | Squat 1RM            | 下肢の最大筋力テスト                    |
| 2    | CMJ                  | カウンタームーブメントジャンプの跳躍高   |
| 3    | Sprint 30m           | 30mスプリントのタイム                   |
| 4    | Y-Balance            | 動的バランス／リーチ左右差のテスト       |

スプレッドシートとはいくつか重要な違いがあるが、リレーショナルデータベースが初めての場合は良い出発点になる。

---

## テーブルが置かれる階層

| 概念 | Neonにおける意味 |
| ---- | ---------------- |
| プロジェクト（Project） | 最上位のコンテナ。ブランチを持つ。 |
| ブランチ（Branch） | データ **とスキーマ** のコピーオンライトなコピー。ブランチごとに独立したテーブルを持つ。 |
| データベース（Database） | ブランチ内のPostgresデータベース（既定は `neondb`）。 |
| スキーマ（Schema） | データベース内の名前空間（既定は `public`）。 |
| テーブル（Table） | 行が保存される場所。 |

**重要:** スキーマはブランチごとに存在するため、開発ブランチで作成したテーブルは、同じDDLを適用する（またはSchema Diff／マイグレーションを使う）まで `production` には **存在しない**。DDLを実行する前に、必ずどのブランチが選択されているかを確認する。

## テーブルの作成

テーブルを作成するときは、列も同時に定義するのが望ましい。各列は作成時に「データ型」を定義しなければならない。列の追加・削除は作成後いつでも可能である。

Neonでのテーブル作成には3つの方法がある。

### 方法1：SQL Editor（再現性の観点で推奨）

1. Neon Consoleを開き、プロジェクトを選択する
2. **SQL Editor** を選択する
3. 対象の **ブランチ** と **データベース** を選択する
4. DDLを入力し、**Run** をクリックする

```sql
create table measurements (
  id bigint generated by default as identity primary key,
  name text,
  description text
);
```

SQL Editorで実行したクエリはAI生成の説明文とともに保存されるため、後から検索・再利用できる。psqlのメタコマンド（例：`\d measurements`）や、自然言語からのSQL生成、エラーのAI修正にも対応している。

### 方法2：Tablesページ（SQLを書かないビジュアル操作）

Neon ConsoleのTablesページは、Drizzle Studio連携によるインタラクティブなGUIである。ここから次の操作ができる。

- レコードの追加・更新・削除（セルをクリックして編集し、**Save x changes** で保存）
- 列の表示／非表示の切り替え、フィルタを **View** として保存
- チェックボックスによるレコードの一括削除
- データの `.json` / `.csv` エクスポート（選択行または全件）
- スキーマの作成・変更・削除
- テーブルとビューの作成・変更、enumの作成
- Postgresロールの作成と `GRANT` 文の組み立て
- テンプレートからのRLSポリシー定義（`neon_rls.md` 参照）
- **Database studio** でスキーマ・テーブル・ビュー・ロール・ポリシーを一覧表示

Tablesページの注意点：

- **新規** レコードを追加する場合、各セルの入力を `Enter` で確定する必要がある。確定せずにタブ移動すると入力が失われる（既存セルの編集では `Enter` は不要）。
- `DEFAULT` を持つ列は空のままにしておけば、保存時にスキーマ定義の既定値が適用される。

### 方法3：クライアント／ORM／マイグレーション

Neonは標準Postgresであるため、任意のPostgresクライアント、ORM、マイグレーションツールが使える（psql、Drizzle、Prisma、Alembicなど）。AI支援開発では、Neon MCPサーバー（`npx neon@latest init`）からブランチに対してDDLを実行できる。

テーブル名は、スペースではなく小文字とアンダースコアを使う（`Table Name` ではなく `table_name`）。

## 列（カラム）

列を作成するときは「データ型」を定義しなければならない。

### データ型

すべての列は事前に定義された型を持つ。Neonは標準Postgresを実行しているため、拡張が提供する型やユーザー定義型を含め、Postgresの型システム全体を利用できる。

| --------------------------------- | ------------- | ------------------------------------------------------- |

| `bit`                             |               | 固定長ビット列                                           |

| `bytea`                           |               | バイナリデータ（バイト配列）                              |
| `character`                       | `char`        | 固定長文字列                                             |
| `character varying`               | `varchar`     | 可変長文字列                                             |
| `cidr`                            |               | IPv4またはIPv6のネットワークアドレス                      |
| `circle`                          |               | 平面上の円                                               |

| `text`                            |               | 可変長文字列                                             |
| `time [ without time zone ]`      |               | 時刻（タイムゾーンなし）                                   |
| `time with time zone`             | `timetz`      | 時刻（タイムゾーンあり）                                   |
| `timestamp [ without time zone ]` |               | 日付と時刻（タイムゾーンなし）                             |

**推奨:** 時刻を扱う列は `timestamp with time zone`（`timestamptz`）を使う。文字列は、長さを制限する明確な理由がなければ `text` を使う。

### 主キー（Primary key）

テーブルは「主キー」を持つことができる。主キーは各行を一意に識別する。

- すべてのテーブルに主キーを作成することが推奨される
- 各行で一意である限り、どの列でも主キーにできる
- `uuid` 型か、採番される `identity` 列を主キーにするのが一般的である

```sql
create table measurements (
  id bigint generated always as identity primary key
);
```

上の例では次のことを行っている。

1. `id` という列を作成した
2. データ型 `bigint` を割り当てた
3. `generated always as identity` を指定し、Postgresがこの列に一意な数値を自動で割り当てるようにした
4. 一意であるため、主キーとしても使用できる

`generated by default as identity` を使えば、自分で一意な値を挿入することもできる。

```sql
create table measurements (
  id bigint generated by default as identity primary key
);
```

UUIDを主キーにする場合：

```sql
create table measurements (
  id uuid primary key default gen_random_uuid()
);
```

`gen_random_uuid()` はPostgres 13以降に組み込まれている（拡張は不要）。

### 行を認証済みユーザーに紐づける

テーブルがユーザー単位のデータを保持し、Data API経由でアクセスされる場合は、ユーザーID列を追加する。Neon AuthのJWTの `sub` クレームは **UUID形式の文字列** であり、Neonは2つのSQLヘルパー関数を提供する。

- `auth.user_id()` → `sub` を `text` として返す
- `auth.uid()` → `sub` を `uuid` として返す

列の型に合わせてヘルパーを選ぶ。

```sql
-- text列の場合
create table condition_logs (
  id bigint generated by default as identity primary key,
  user_id text default (auth.user_id()) not null,
  fatigue smallint not null,
  logged_at timestamptz default now() not null
);

-- uuid列の場合
create table condition_logs_uuid (
  id bigint generated by default as identity primary key,
  user_id uuid default (auth.uid()) not null,
  fatigue smallint not null
);
```

列の `DEFAULT` にヘルパー関数を設定しておくと、新しい行は自動的に現在のユーザーへ紐づけられる。クライアントがユーザーIDを送る（あるいは偽装する）必要がなくなる。`neon_rls.md` を参照。

## データの投入

Neonへのデータ投入方法は複数ある。SQLの `INSERT`、Tablesページの **Add record** ボタン、psqlからの `\copy` / `COPY`、Data API経由などである。大量データの場合は `COPY` を使う。

### 基本的なデータ投入

```sql
insert into measurements
  (name, description)
values
  (
    'Nordic Hamstring',
    'ハムストリングスのエキセントリック筋力テスト'
  ),
  (
    'Isometric Mid-thigh Pull',
    '等尺性最大発揮筋力テスト'
  );
```

## 外部キーによるテーブルの結合

テーブルは外部キー（Foreign Key）で結合できる。

```sql
create table categories (
  id bigint generated always as identity primary key,
  name text -- カテゴリー名
);

alter table measurements
  add column category_id bigint references categories;
```

「結合テーブル」による多対多の関係：

```sql
create table measurements (
  id bigint generated by default as identity primary key,
  name text,
  description text
);

create table athletes (
  id bigint generated by default as identity primary key,
  name text
);

create table results (
  id bigint generated by default as identity primary key,
  measurement_id bigint not null references measurements,
  athlete_id bigint not null references athletes
);
```

絞り込みや結合に使う外部キー列にはインデックスを追加する。

```sql
create index results_athlete_id_idx on results using btree (athlete_id);
```

## スキーマ

テーブルは `スキーマ` に属する。スキーマはテーブルを整理する仕組みであり、しばしばセキュリティ目的で使われる。

テーブル作成時にスキーマを明示しない場合、Postgresは `public` スキーマに作成すると解釈する。

```sql
create schema private;

create table private.salaries (
  id bigint generated by default as identity primary key,
  salary bigint not null,
  athlete_id bigint not null references public.athletes
);
```

Neonプロジェクトで重要なスキーマ：

| スキーマ | 内容 | 備考 |
| -------- | ---- | ---- |
| `public` | アプリケーションのテーブル | 既定でData APIに公開される |
| `neon_auth` | Neon Auth（Managed Better Auth）のデータ：`user`、`account`、`session`、`verification` | Neon Authが管理する。SQLで参照可能だが、直接書き込まない |
| `auth` | ヘルパー関数 `auth.user_id()`、`auth.uid()`（`pg_session_jwt` 拡張由来） | Data APIを有効化すると利用可能 |

`public` 以外のスキーマをData APIに公開する場合は、Data APIの **Settings** タブで公開スキーマを設定し、権限を明示的に付与する。

## ビュー（View）

ビューはクエリへのショートカットである。ビューを作成しても新しいテーブルやデータは生成されない。

```sql
create view athlete_results as
    select
        athletes.name as athlete,
        measurements.name as measurement,
        results.id as result_id
    from results
    left join athletes on results.athlete_id = athletes.id
    left join measurements on results.measurement_id = measurements.id;

grant all on table athlete_results to authenticated;
```

### ビューのセキュリティ

既定では、ビューは作成者の権限でアクセスされる（security definer）。これは **元テーブルのRLSポリシーをバイパスする** ことを意味する。クエリを実行したユーザーのRLSを適用するには、security invoker修飾子を付けてビューを定義する（Postgres 15以降）。

```sql
create view <view name> with(security_invoker=true) as (
  select * from <some table>
);
```

**これはよくある情報漏洩経路である。** `security_invoker=true` を付けずにビューをData APIへ公開すると、RLSが本来隠すべき行を認証済みユーザーが読み取れてしまう。

### マテリアライズドビュー

マテリアライズドビューは結果をディスクに保存し、読み取りを高速化する。

```sql
create materialized view athlete_results_cached as
  select ...;

-- 定期的にリフレッシュする：
refresh materialized view athlete_results_cached;
```

マテリアライズドビュー自体はRLSに対応しないため、権限を付与したロールに対しては全公開だと考えて扱う。

## スキーマ変更後にやること（Neon固有）

### 1. Data APIのロールに権限を付与する

Data APIは、有効なJWTがあれば `authenticated` ロール、トークンがなければ `anonymous` ロールとしてクエリを実行する。デフォルト権限を設定していない場合、新しく作成したテーブルは読み取れない。

```sql
-- 1. スキーマへのUSAGE権限
GRANT USAGE ON SCHEMA public TO authenticated;

-- 2. 既存テーブルへの権限
GRANT SELECT, UPDATE, INSERT, DELETE ON ALL TABLES
  IN SCHEMA public TO authenticated;

-- 3. 今後作成されるテーブルへ自動的に権限を付与
ALTER DEFAULT PRIVILEGES IN SCHEMA public
  GRANT SELECT, UPDATE, INSERT, DELETE ON TABLES TO authenticated;

-- 4. シーケンスへの権限（自動採番IDに必要）
GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA public TO authenticated;
```

ConsoleからData APIを有効化する際に **Grant public schema access** をチェックすると、上記が自動で適用される。テーブル作成直後の「permission denied」エラーは、通常この権限不足が原因である。

### 2. Data APIのスキーマキャッシュを更新する

Data APIはスキーマをキャッシュしている。テーブル追加、列の追加・変更、構造変更を行った後はキャッシュを更新しないと、変更がREST経由で反映されない。

- **Console:** Data APIページ → **Refresh schema cache**
- **API:** `PATCH /projects/{project_id}/branches/{branch_id}/data-api/{database_name}` に空のボディ（`-d '{}'`）を送る

### 3. RLSは自動で有効にならない

Neonでテーブルを作成しても、Row Level Securityは **有効にならない**。Data APIから到達可能でRLSが無効なテーブルは、すべての認証済みユーザーが全行を読める。Data APIページには警告と **Enable RLS** ボタンが表示され、Tablesページにはポリシーのテンプレートがある。`neon_rls.md` を参照。

```sql
alter table condition_logs enable row level security;
```

## 付録：Supabase → Neon 対応表（テーブル）

| Supabase | Neon | 備考 |
| -------- | ---- | ---- |
| Table Editor | **Tables** ページ（Drizzle Studio） | スプレッドシート的な編集は同等。NeonはDatabase studio、ロール作成、RLSテンプレートを持つ |
| SQL Editor | **SQL Editor** | Neonはpsqlメタコマンドとクエリ履歴、AIによるSQL生成に対応 |
| Table EditorでRLSが自動有効 | **自動では有効にならない** | `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` または **Enable RLS** が必要 |
| `auth.users`（`auth` スキーマ） | `neon_auth.user`（`neon_auth` スキーマ） | Neon Authは自分のDBにIDを保存する |
| `auth.uid()` が `uuid` を返す | `auth.uid()` → `uuid`、`auth.user_id()` → `text` | ヘルパーが2つある。列の型で選ぶ |
| `anon` ロール | `anonymous` ロール | 名称が異なる |
| PostgREST（常時有効） | **Data API**（ブランチごとに任意で有効化） | 有効化が必要。DDL後はスキーマキャッシュ更新も必要 |
| プロジェクト＝1環境 | **ブランチ** | スキーマ・データ・認証状態がまとめて分岐する |
